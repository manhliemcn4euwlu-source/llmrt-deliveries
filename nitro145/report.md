# NitroMTA 0.2.0: one real delivery, unprivileged user, Ubuntu x86_64

- **Version and install**: `nitromta-0.2.0-x86_64-linux.tar.gz` (10,208,520 bytes) from the v0.2.0 GitHub release, extracted with `tar xzf` into an empty directory, run directly. `nitromta --version` printed `nitromta 0.2.0`. No root, no package manager, no container.
- **OS and architecture**: Ubuntu 26.04.1 LTS, Linux x86_64, one CPU, no domain of my own and no DNS records.
- **Setup**: `nitromta setup --config config.toml --capture` wrote `config.toml`, `tls.crt`, `tls.key` and `keys`, and printed the admin recipe. The archive listing held the binary, README, LICENSE, NOTICE, a systemd unit and a sysusers file, so the binary path is `nitromta-0.2.0-x86_64-linux/nitromta`.
- **Every config.toml change**: deleted the whole `[capture]` section, set `port = 2525` under `[delivery]`, set `dane = false` under `[delivery]`. Nothing else was edited, and `[store]`, `[submission]`, `[ses]`, `[admin]` and `[operator]` kept the values setup wrote.
- **Start**: `nitromta run --config config.toml` as my own user. It logged `serving admin`, `accepting submission` on `127.0.0.1:2587`, `serving the SES v2 API` on `127.0.0.1:4443` and `serving health and metrics` on `127.0.0.1:9090`. The first attempt exited with `127.0.0.1:2587: Address already in use` because an older NitroMTA build of mine was still bound to that port; stopping that process and starting again was the only retry.
- **Policy**: `openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out dkim.pem`, then three lines piped to `nitromta admin --config config.toml`: `put_account` with `account: 1`, `put_identity` with `name: llmrt-proof.test`, `selector: s1` and the PEM as a JSON string, and `create_login` with `user: app`. The admin socket answered `revision 1`, `2` and `3` and returned the login password once.
- **Send**: Python 3.12 `smtplib.SMTP('127.0.0.1', 2587)` with `STARTTLS` against the generated `tls.crt`, `login('app', ...)`, `sendmail` from `proof@llmrt-proof.test` to `proof@nitromta.com`, `Reply-To` set to my own readable mailbox. The submission was accepted on the first attempt with an empty refusal dict.
- **Delivery proof on my side**: `127.0.0.1:9090/metrics` showed `nitromta_attempts_total{result="delivered"} 1` and `{result="captured"} 0`, which confirms the `[capture]` section really was gone and the message left the machine rather than being written to disk.
- **Receipt**: the proof mailbox answered with `https://runx.ai/r/f7b6cb213944ab83a1a9e4a197b668c88db68f67b302bf65d5c615838a65c62f`, recording arrival at 2026-11-04T03:30:11.822Z.
- **Minutes from install to the receipt**: about 3. Download and extract took under 1, setup and policy about 1, the send under 1, and the receipt arrived inside the same minute.
- **The step that slowed me down most**: the port collision, and what made it slow is that it is invisible in the engine's own output until the run fails. `nitromta run` logs `serving admin` and only then reports the bind error, so a first-time user reads a success line before the failure.
- **Doc gap with an exact repro**: the admin recipe that `nitromta setup` prints shows `put_identity` with only `account` and `name`, while an identity that must sign needs `selector` and `private_key` as well. Repro: run `nitromta setup --config config.toml --capture`, read step 2 of the printed recipe, then look at the field list in `docs/install.md`; the two disagree and the printed version is the one a first-time user follows. The same recipe also shows `create_login` without saying the password is returned once in the reply and cannot be read back, so it is easy to lose.
- **One change I would make**: have `nitromta run` print the resolved `[delivery]` `port` and `dane` values and the store path next to its `serving` lines, so a user can confirm the edited config was parsed without waiting for a delivery to succeed or fail.
