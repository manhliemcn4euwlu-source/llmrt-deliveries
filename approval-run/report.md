# Safe Mode approval loop, run end to end over the Nitrosend HTTP API

- Install and commands. The Nitrosend side used Python 3.14.0 `urllib` only, against `https://api.nitrosend.com`, no SDK, no browser. `mailschema@0.3.2` was installed through `npx --yes mailschema@0.3.2` on Node v22.22.1. The contract came from `https://mailschema.org/artifacts/map-0.3/contracts/campaign-send-approval-0.1.json` (HTTP 200, 10499 bytes).
- The send receipt this account needed first. Five `POST /v1/my/messages` calls to `proof@dogfood.nitrosend.net` from `hello@llmrt142.nitrosend.net` were accepted and `GET /v1/my/messages/sends` reported `transactional: 5, sent: 5, delivered: 5`, yet none of them produced a receipt email. A `nitrosend send` through `@nitrosend/cli` 0.3.8 (message 5226214, 2026-10-28 08:02:13 UTC) produced `Your Nitrosend send receipt` two seconds later. That is the finding below.
- Brand Kit address and Safe Mode. `PATCH /v1/my/brands/b435e6062cd6f4313739b81b` with `physical_address` as a plain string returned 200 and `GET /v1/my/campaigns/<id>/readiness` reported `physical_address: passed`. `PATCH /v1/my/account {"safe_mode_enabled": true}` returned 200 and read back true.
- Campaign authoring. `POST /v1/my/campaigns {"name":"proof"}` answered 201 with an empty draft; subject, audience and body are not accepted there. A `PATCH /v1/my/campaigns/<id>` carried `trigger_attributes: {"event":"scheduled","audience_type":"lists","contact_list_ids":[12932]}` and `template_attributes: {"if_version":N,"subject":...,"design":{"version":1,"sections":[{"type":"text","props":{"content":...}}]}}` and returned 200. A `text` section rejects `props.text` and requires `props.content`; `content_format: plain` is refused because the draft was created as `designed`.
- Safe Mode hold. `POST /v1/my/campaigns/<id>/send` requires `expected_campaign_updated_at` (the exact persisted timestamp) and `template_if_version`; sending `if_version` instead returns 422 `invalid_campaign_send_options`. With the two correct keys it returned 200, `delivery.state: awaiting_approval`, `delivery.wait_reason: manual_approval`, and `delivery_approval.id: 465`.
- Approval email. It arrived four seconds after the hold, from `contact@nitrosend.com`, subject `Review send request: Copy of Copy of proof`. It is `multipart/related` holding `multipart/alternative` plus one `application/ld+json` part whose `Content-Type` carries `profile="https://mailschema.org/profiles/map/0.3"`; the part is quoted-printable and decodes to the description unchanged.
- Extract. `npx --yes mailschema@0.3.2 message tmp/_loop3_6ae1ad64.eml > tmp/description3.json`, exit 0, stderr `Valid MAP 0.3 description urn:uuid:93f7ef63-c60f-5e45-bd2b-f9217b9e8090` and `sha-256:d92c34bd3ba03bdbd45d78ade09072b56ff5c17d6105104acec50f7535c98a00`.
- Validate. `npx --yes mailschema@0.3.2 description tmp/description3.json --contract tmp/campaign-send-approval-0.1.json` printed `Valid MAP 0.3 description urn:uuid:93f7ef63-c60f-5e45-bd2b-f9217b9e8090` and the same `sha-256:d92c34bd...`, exit 0.
- Version recomputation. A Node script imports `digest` from `mailschema`, deep-copies the parsed description, deletes `terms.version`, and digests the rest: `sha-256:6b28c07569eade7b1a2c3174d98d015f3a12dbf3e74dd5877d4e330d77cdbcf9`, equal to the `terms.version` the document carries. The document digest above is a different value, as it must be.
- Decision: approve. The description names campaign 15483, one contact list holding two subscribed contacts, sender `hello@llmrt142.nitrosend.net`, `schedule.mode: immediate`; the digest recomputes and every address involved is mine, so approving exercises the release path this run exists to check.
- Decision call. `POST /v1/my/map/approvals/465 {"decision":"approve","version":"sha-256:6b28c075..."}` with the account owner's own sign-in returned 200, `state: approved`, `decided_at: 2026-10-28T08:09:44.790Z`.
- Receipt. `Your Nitrosend send approval receipt` arrived at 08:09:51Z carrying `https://runx.ai/r/ece19f11e7cfda660437061d5514994c4cb0a73f7a0d53c0a9fef59e164c4dbe`. Fetching it returns 200 and its claim names `api.nitrosend.com/v1/my/map/approvals/465`, exactly the `terms.id` in the description.
- Minutes from the Safe Mode hold to the decision. The hold was created at 08:08:03Z and the decision landed at 08:09:44Z: one minute forty-one seconds, of which the extract, validate and digest steps took about twenty seconds and the rest was polling for the email.
- Step that slowed me most. Discovering that a receipt is issued only to a send that came through the CLI, SDK or MCP client. Five REST `POST /v1/my/messages` sends were accepted and delivered and produced no receipt at all; the same content through the CLI produced one in two seconds, and only after that did an approval decision issue a receipt.
- One defect with an exact repro. `PATCH /v1/my/brands/<sid>` accepts `physical_address` as a JSON object and answers 200 while storing nothing; `GET /v1/my/campaigns/<id>/readiness` then reports `physical_address: failed` with no hint that the shape was the cause. The same value as a string stores it and the check passes.
- Second defect with an exact repro. `POST /v1/my/campaigns/<id>/send` refuses `if_version` with 422 `invalid_campaign_send_options` and wants `expected_campaign_updated_at` plus `template_if_version`, while the `PATCH` on the same campaign requires `if_version`. Neither error names the other spelling.
- Third defect with an exact repro. The approval receipt email carries four runx links that share one prefix and differ only in length (`...a`, `...0a`, `...d53c`, then the full 64 hex characters). Only the longest resolves; the other three return 404 `Receipt not found`. A reader who copies the link from a wrapped line gets a dead page.
- One change I would make. Return the same receipt for a REST send that the CLI send gets, or say in the send response that no receipt will be issued for that route. The account had already delivered five messages when it still counted as having no receipt.
